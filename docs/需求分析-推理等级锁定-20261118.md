# 需求分析：默认推理等级锁定

- 插件：`dsh-pin-default-model`
- 当前版本：1.2.0
- 目标版本：1.3.0
- 日期：2026-11-18

---

## 1. 需求描述

在现有「默认模型锁定」基础上，增加**默认推理等级（reasoning effort）锁定**：

- 新建会话使用锁定的推理等级
- 默认值为 `high`
- 会话内临时切换推理等级仍然只对该会话生效，不改写锁定值

---

## 2. 已核实的现状（源码级）

### 2.1 数据链路

```
agentDefaultModel.currentSelection()  →  { provider, model, reasoningEffort? }
        │                                        （三个字段都是 Volatile 配置引用）
        ├─→ AgentOptions.reasoningEffort  （getter，实时读取）
        │        └─→ 新会话的 Agent 用它作为初始推理等级
        │
        └─→ saveSelection(next)  →  configEditor.edit(entry, () => config)
                 └─→ 写入 profile 的 agent-default-model 条目
```

会话内切换走 `sessionController.selectModel(request)`（`dsh-api-session-controller/src/commands.ts:166`）：

```ts
agent.model.select(selected);                                  // 会话内立即生效
void this.ctx.agentDefaultModel.saveSelection(selected);       // 顺手改写全局默认值 ← 要拦截的就是这条
```

`selected` 是三元组 `{ provider, model, reasoningEffort? }`，**推理等级本来就在被改写的范围内**。

### 2.2 现有拦截逻辑已天然覆盖 effort

`lib/index.js` 的 `keyOf()` 已经按三元组比较：

```js
[provider, model, reasoningEffort].join('\u0000')
```

所以只要 `pin` 里带上 `reasoningEffort`：

- 会话内只切 effort 不切 model → `keyOf(next) !== pinKey` → **被拒绝**，默认值不被改写 ✓
- `hold()` 漂移修复也按三元组比对 → effort 一起恢复 ✓

**host 端拦截逻辑无需重构，只需让 pin 携带 effort。**

### 2.3 effort 是 model-specific 的（关键约束）

`dsh-llm/src/index.ts:913` `resolveCallConfig()` 是**硬校验**：

| 情况 | 行为 |
| --- | --- |
| 模型无 reasoning，但请求了 effort | 抛 `UNSUPPORTED_REASONING_EFFORT` |
| 请求的 effort 不在该模型的 efforts 列表里 | 抛 `UNSUPPORTED_REASONING_EFFORT` |

这意味着 **锁定的 effort 不被当前模型支持时，新会话会直接失败**，不是降级。

### 2.4 实测模型目录（当前 profile，2026-11-18）

当前锁定：`magpie/group/x-call` → efforts `[high]`，无 defaultEffort。

各模型的 effort 覆盖面差异极大：

| 模型 | efforts | default |
|---|---|---|
| `magpie/group/x-call` | `high` | — |
| `magpie/workbuddy/space-bunny` | `low,medium,high,xhigh,max` | — |
| `magpie/workbuddy/minimax-m3.1-flash` | `low,medium,high,xhigh,max` | — |
| `magpie/openrouter/liquid/lfm-3-1.7b:free` | **（无 reasoning）** | — |
| `magpie/kilo/kilo-auto/free` | **（无 reasoning）** | — |
| `magpie-anthropic/tokenhub/minimax-m3` | **（无 reasoning）** | — |
| `deepseek-account/deepseek-flash` | `off,low,high,max` | `high` |

注意：

- 很多模型支持 `off`（关闭推理）
- **约 10 个模型完全没有 reasoning**，这类模型**任何 effort 都不能锁**，连 `off` 也不行
- `high` 是所有支持 reasoning 的模型都有的档位，覆盖面最好

### 2.5 顺带发现的既有 Bug（需一并修）

`client/client.js` 当前把 `efforts` 当**对象**处理：

```js
const efforts = model?.reasoning?.efforts;
return Object.keys(efforts).filter((k) => efforts[k] !== false);   // ❌
```

但实际类型是**数组**（`dsh-api-session-controller/src/types.ts:106`）：

```ts
readonly efforts: readonly ModelReasoningEffort[]   // [{ id, name, description? }]
readonly defaultEffort?: string
```

数组走 `Object.keys` 会得到 `["0","1","2"]`，下拉框会显示 `0`/`1` 这种垃圾值。

现在没暴露，纯粹是因为当前模型 `magpie/group/x-call` 的 reasoning 元数据在界面里没被正确读取到 effort 下拉。**加了 effort 锁定后这个 bug 必然暴露，必须同时修。**

## 3. 功能需求

### F1 设置页：推理等级下拉

- 在模型下拉框旁增加「推理等级」下拉
- 选项来自**当前选中模型**的 `reasoning.efforts`，显示 `name`，取值 `id`
- 提供「跟随模型默认」选项（值为空）
- 模型切换时，effort 选项列表跟着换
- 若当前锁定的 effort 不在新模型的列表里，给出明确提示

### F2 锁定语义

- `pin` 扩展为 `{ provider, model, reasoningEffort? }`
- `reasoningEffort` 缺省时：
  - **跟随模型默认**（不写入 effort，等于 DSH 原生行为）
- 界面上默认值呈现为 `high`（当模型支持时）

### F3 默认值 high

插件配置 `reasoningEffort` 未设置时按 `high` 处理。

> ⚠️ 此项与 F2 的「跟随模型默认」有冲突，见下方决策点 D1。

### F4 持久化

- 锁定值写入 profile，重启后保持
- `saveSelection` 写入 `agent-default-model` 条目时带 `reasoningEffort`
- 已核实：`provider`/`model` 同为 Volatile 字段却确实写进了 profile，Volatile 不阻止持久化

### F5 会话内行为不变

- 会话内切模型/切 effort → 该会话生效，默认值不变
- 自动化任务创建的新会话 → 使用锁定的模型 + effort

---

## 4. 风险

| 级别 | 风险 | 说明 |
| --- | --- | --- |
| **高** | effort 与模型不兼容导致会话创建失败 | `resolveCallConfig` 硬校验，抛 `UNSUPPORTED_REASONING_EFFORT` |
| **高** | 锁定 `high` 但切到无 reasoning 的模型 | 该模型任何 effort 都不支持，会话直接失败 |
| **中** | 模型切换后锁定值失效 | 换模型后原 effort 可能不在新列表里 |
| **中** | `off` 语义歧义 | `off` 表示关闭推理，但仍属 effort 列表项，不能当「跟随」用 |
| 低 | 客户端 efforts 数组处理错误 | 见 2.5，必须修 |
| 低 | effort 值随 provider 变化 | 不同 provider 的档位命名不统一（`xhigh` / `minimal` / `medium`） |

## 5. 待决策项

### D1 「默认 high」的确切语义

| 方案 | 描述 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | 配置缺省 = **跟随模型默认**；UI 默认展示并推荐 `high` | 对无 reasoning 的模型天然安全，不会把会话搞挂 | 不完全等于「强制 high」 |
| B | 配置缺省 = 强制 `high` | 严格符合字面需求 | 切到无 reasoning 模型会**直接失败** |
| C | 缺省 = 强制 `high`，但**运行时校验**：模型不支持时自动落到该模型的 `defaultEffort` 或最高档 | 兼顾字面需求与安全 | 行为不完全可预测，需要额外提示 |

> 当前锁定的 `magpie/group/x-call` 只支持 `high`，所以 A/B/C 在**当前配置下行为完全一致**。差异只在主人日后换到别的模型时才显现。

### D2 模型不支持锁定 effort 时的处理

| 方案 | 描述 |
| --- | --- |
| **A（推荐）** | 设置页明确警告 + 提供「一键跟随模型默认」；不做自动降级 |
| B | 运行时自动降级到 `defaultEffort`（无则最高档），日志记录 |
| C | 保持失败，让主人自己发现 |

> 选 A 需要在设置页做到「当前模型不支持此 effort」的提示足够醒目。

### D3 是否允许「跟随模型默认」作为一个可选锁定值

需要锁定值本身能表达「不锁 effort」。当前 `cleanSelection` 已支持省略 effort，但要确认这在语义上与「锁定 effort」区分得开（我倾向用**字段缺省**表达跟随，不引入哨兵值）。

## 6. 实现方案概要

### 6.1 host 端（`lib/index.js`）

改动不大：

1. `FALLBACK_PIN` 增加 `reasoningEffort`（按 D1 结论定）
2. `readPin` / config 读取：处理 effort 缺省与校验
3. `/dsh-pin-model/set` 路由：接受并保存 `reasoningEffort`
4. `/dsh-pin-model/view` 路由：返回锁定值（含 effort）
5. `hold()` 漂移修复：三元组已覆盖，无需改

**校验点**：写 pin 时，若锁定模型不支持该 effort，host 端应**拒绝并返回明确错误**（而不是等到会话创建时才炸）。

### 6.2 客户端（`client/client.js`）

1. **修 efforts 数组 bug**：`model.reasoning.efforts.map(e => e.id)`，显示 `e.name`
2. 新增 effort 下拉，选项随当前模型联动
3. 「跟随模型默认」选项
4. 当前锁定展示加上 effort
5. 不兼容提示（按 D2 结论）

### 6.3 配置与文档

- `cordis.patch.yml` 增加 `reasoningEffort` 示例
- README 中英文补充 effort 锁定说明与「模型必须支持该档位」的警告
- 版本号 → 1.3.0
- 重新生成 preview 配图（含 effort 控件）

## 7. 验收标准

1. 设置页出现「推理等级」下拉，选项为当前模型支持的档位（含显示名）
2. 选择 `high` 保存后，重启 DSH 锁定值仍在
3. 新建会话使用锁定模型 + `high`
4. 会话内切换 effort → 该会话生效，默认锁定值不变
5. 会话内切换模型 → 默认锁定值不变
6. 切换到不支持 `high` 的模型 → 设置页给出明确警告，不静默失败
7. 自动化任务创建的新会话同样使用锁定模型 + effort
8. 现有测试全部通过，新增 effort 相关测试
